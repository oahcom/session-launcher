## 一、成功判据的精确化：「接入完成」是什么意思

「把 opencode 接入三项目，与 claude 同级，后续可以选择不同 agent 启动」在工程上必须落成六个**可检验命题**——每个命题都有对应的证据协议（第五节），没有证据不算达成：

| 命题 | 含义 | 检验方式概要 |
|------|------|--------------|
| P1 同级生命周期 | opencode 会话走与 claude 完全相同的六条链路入口（启动/投递/判活/自愈/上下文/状态），链路代码对两引擎行为等价 | 双引擎端到端冒烟 |
| P2 可选择且持久 | 启动时能声明引擎：角色默认（persona 字段）+ 单次覆盖（CLI 参数）；选择结果持久化 | 两种入口各取证 + 哨兵记录核对 |
| P3 不翻转 | 任何自动重启拉起的引擎与出生时一致，只认持久化的事实，不认任何推断 | 故障注入自愈后核对 |
| P4 claude 零回归 | 不带新参数时，全部现有行为与改动前语义等价 | claude 全链对照 + 分支改动面审查 |
| P5 评估诚实 | 观测/评估面对 opencode 会话显式标注「未纳入」，无静默假阴性 | 对 opencode 会话跑评估入口取证 |
| P6 codex 不受损 | codex 孤岛行为不变 | codex 子命令冒烟 |

「同级」在此不是修辞：指**生命周期操作的集合与语义**对两引擎一致（创建、投递、判活、自愈、上下文、状态可见），而不是「两个二进制都能跑」。「可选择」也不止「有个开关」：开关必须能表达角色级偏好与按次试跑两种诉求，且选择在进程死亡后仍然有效——否则「选择」在自愈系统里是一次性的幻觉。

## 三、根因排序与修改论证（最根本 → 最表层）

排序原则：按「离『身份从哪来』的距离」排序，不按修复成本排序。每层给足【问题 → 为何影响 → 如何影响 → 修改的因果逻辑 → 为何能解决 → 残余风险】。本节是论证，不是步骤。

### 第 1 层（最根本）：引擎成为一等概念——身份的「声明→选择→事实→消费」闭环

【问题】全系统无一处回答「这个会话由哪个引擎承载」。persona 无声明位、CLI 无选择位、哨兵虽有字段但出生时无人写、消费时靠会话名前缀反推。身份处于「有存储、无闭环」状态。

【为何影响】这是其余一切硬编码的共同根因：正因为无 engine 可查，判活、投递、上下文、评估才各自写死 claude。

【如何影响】换引擎的任何改动都退化为「二十余处字面量替换」，且自动重启路径拉错引擎的故障面无法从结构上关闭——替换漏一处就翻车，而漏网只能靠运气发现。

【修改的因果逻辑】建立三层声明加一条消费规则：**声明层**（persona 增 engine 字段，表达角色级默认）→ **选择层**（start 的 CLI 增引擎参数，表达按次覆盖）→ **事实层**（启动时把最终值写入哨兵 engine 字段，成为唯一事实源）→ **消费规则**（一切分派只读哨兵 engine，禁止新增任何推断）。前缀反推逻辑降级为「无哨兵时的回退」，且语义与 codex 兼容不动。

【为何能解决】身份有了唯一事实源后，「翻转」在结构上不可能——消费方不再发明推断，就没有两个真相打架的可能；「可选择」语义完整落在两个声明入口（长期偏好 + 临时试跑）。注意解决的不是「哪里存 engine」而是「谁是真相」：只加字段不立消费规则，仍会回到多方推断的老路。

【残余风险】历史哨兵文件缺 engine 键——反序列化已有默认值兜底，旧会话读出 "ccs" 与旧行为一致，风险闭合。persona 批量加字段需同步契约版本号，防 schema 漂移。

### 第 2 层：启动面（进程出生）按引擎分派

【问题】出生地唯一（wrapper 构造处），但命令行、环境注入、就绪判据三件套都是 claude 形状。

【为何影响】出生地是身份的物理起点；此处不分派，后续五条链服务的就是错的进程，上游声明再正确也白搭。

【如何影响】照搬现状起 opencode，要么拉错二进制，要么拉起后就绪探测永不命中（探测看的是 claude 提示符），会话卡死在「已创建未就绪」——而监控可能显示一切正常。

【修改的因果逻辑】wrapper 构造按引擎分派：claude 分支逐字不动（含 ANTHROPIC_* 注入与启动后断言——那套是 claude 的认证方式，缺了会静默卡登录页）；opencode 分支拉起 opencode TUI，跳过 ANTHROPIC_*（其模型出口走自身 provider 配置，实测已通），就绪判据换成 opencode 侧特征（候选：输入占位提示或版本角标；**落码前须真机标定**，不许沿用 claude 判据）。两分支共用 while-true 重拉骨架。

【为何能解决】进程身份从源头正确；claude 分支零改动直接兑现 P4 的主体；opencode 免配置模型链路（同一 9Router）使改造面收窄到形态分派本身。

【残余风险】就绪判据误判（假就绪→投递落入未就绪 TUI）。对策：判据参数化 + 失配显式报错，禁止静默放行。

### 第 3 层：判活与自愈按引擎

【问题】三处判活（watchdog 双检的进程扫描、健康检查的 cmdline 扫描、陈旧重启的 comm 严格匹配）与两处自动重启入口（watchdog 侧、pipeline 侧）全部写死 claude。

【为何影响】判活是自愈系统的感官，重启是自愈系统的手。感官写死 → 误判；手写死 → 误救。

【如何影响】opencode 会话被判「无 claude 进程」→ 判死/判僵尸 → 自动重启走启动链拉 claude → **引擎翻转**：身份、上下文文件、模型配置三重错位，而监控指标显示「已恢复」。这是最恶性的故障形态——错误被自愈系统洗白。

【修改的因果逻辑】判活三处统一为「按引擎取进程名」（进程查找函数已参数化，codex 先例可循）；两处重启入口从哨兵读 engine 并透传给启动（启动面即第 2 层的分派入口）。哨兵缺失时回退规则保守：前缀推断 → 默认 ccs，与旧行为一致。

【为何能解决】感官与行为同源（都读 engine）：误判面与误救面同时消除，P3 落地。关键是「同源」而非「多处各改各的」——三处判活若各自发明引擎识别规则，等于重造推断混乱。

【残余风险】哨兵文件损坏/缺失瞬间的重启决策。回退链（前缀→默认）保证该瞬间行为与改造前一致，不引入新故障面。

### 第 4 层：TUI 交互协议按引擎

【问题】投递三判据（忙判据文案、composer 几何、提交确认判据）绑定 Claude TUI 形状；实测 opencode 三样全不同（忙标记无 to、composer 竖线几何）。

【为何影响】投递正确性整体建立在「pane 里跑的是 Claude TUI」的假设上。假设破裂的代价有实证：生成中被投递 → 在飞推理被覆盖（closer 实测 9 分 58 秒推理被冲掉）；提交判据失效 → 消息滞留输入框（archivist 实测滞留 25 分钟）。

【如何影响】opencode 照搬 claude 判据两头出事：忙漏判（"esc interrupt" 不匹配 "esc to interrupt"）→ 生成期误投 → 覆盖在飞推理；composer 几何不匹配 → 提交确认取不到区域 → 反复补 Enter 空转或滞留不可见。

【修改的因果逻辑】判据按引擎分派，投递骨架（清行/粘贴/Enter）两引擎共用不动。忙判据：claude 沿用现文案，opencode 用实测串——两串互不为子串（"esc to interrupt" 不含连续的 "esc interrupt"），匹配必须整串精确，防误伤。composer 与提交确认按引擎取几何规则。判据失配时显式报错。

【为何能解决】两类实证事故的防护在 opencode 上恢复等效强度；因为只换判据不动骨架，claude 行为零漂移。判据收口进引擎配置表（一处集中、按引擎取值）而不是散点 if，直接回应「防退化」要求。

【残余风险】TUI 文案随版本漂移（现版本已提示 1.19.5）。对策：判据参数化 + 版本基线记录 + 失配显式报错（假闲是最危险的降级方向，禁止）。

### 第 5 层：上下文按引擎落盘

【问题】角色知识注入写 CLAUDE.md；opencode 实测只认 AGENTS.md（本轮复现）。

【为何影响】「上下文隔离、互不污染」这一项目核心价值，物理上落在指令文件名上。文件名错 = 空脑运行。

【如何影响】opencode 角色进程活着、消息进得去，但契约/红线/教训一样读不到，产出质量塌方且**无任何报错**——正是「进程在转 ≠ 角色在高质量产出」的最隐蔽形态。

【修改的因果逻辑】知识渲染管线保持单一（同源），落盘目标按引擎取文件名（claude→CLAUDE.md，opencode→AGENTS.md）；注入时机仍在启动前（与现链一致：指令文件是启动时读入的，先注后启）。MCP/权限配置（.claude/settings.json）一期不向 opencode 映射，但必须显式声明已知限制——**不许默认「已隔离」**。

【为何能解决】同源生成保证两引擎拿到的角色知识逐字一致（防双份漂移）；按名落盘消除空脑。把「已知限制」写成显式声明，是把潜在的假阴性（以为隔离了）提前变成真阳性（知道没隔离）。

【残余风险】双文件的重注入时序（覆盖/更新时两份必须同步替换）。对策：同源单次渲染、同步落盘，作为不变量写进自验。

### 第 6 层：观测/评估面显式降级

【问题】评估取数的四个消费点（转录解析、评估器、工作流生命周期、意图分类器）硬编码 claude 转录目录布局。

【为何影响】opencode 会话的产出在评估面静默缺席——不是「评了差分」而是「根本没被评」，形成假阴性。

【如何影响】质量信号失真：坏产出无痕迹，好产出也不计分。对一个以质量管控为生命线的系统，评估面静默失明比没有评估更危险（因为它制造「已评估」的错觉）。

【修改的因果逻辑】一期不接通 opencode 转录存储（二期做），但四个消费点对非 claude 布局的会话返回**显式「未纳入评估」标记**，且标记进入与评估结论同级的可见面（健康面板/状态输出），禁止默认通过或静默空集。

【为何能解决】P5 的诚实性：「没评」在任何界面上都不可被误读为「评过且合格」。降级点同时是二期接入点，届时替换实现不动调用语义。

【残余风险】标记只写日志会被忽略。对策：标记必须进状态可见面，交叉审查按「可见性」验收。

### 第 7 层（最表层）：命名空间解耦与推断反转

【问题】引擎推断靠会话名前缀（前缀反推处 sentinel.py:291/:348），命名空间与引擎语义纠缠。

【为何影响】D1 已定「沿用 ccs- + engine 存哨兵」：命名空间承载「会话族」语义，engine 承载「实现体」语义，二者必须解耦，否则 opencode 会话在 ccs- 族里会被反推成 claude。

【如何影响】若不反转推断优先级，第 1 层写入的哨兵 engine 会在「无哨兵重建/前缀路径」被覆盖回 claude——第 3 层的防翻转就在这里被击穿。

【修改的因果逻辑】engine 读取优先级反转：哨兵 engine 优先，前缀反推只作无哨兵时的回退（cdx→codex 逻辑不动，P6 保住）。make_tmux_name 与存活快照过滤零改动（D1 的全部收益正在于此：send/liveness/feed 对新引擎天然透明）。

【为何能解决】一处优先级反转，换四五处过滤器扩散的消除；且把「推断」钉死在唯一合法用途（无事实源时的兜底）。

【残余风险】无新增。回退路径语义与改造前一致。

## 四、因果闭环：七层如何合成「同级」

六条链与七层的对应关系（缺一层，「同级」在对应链上塌方）：

| 链 | 合成层 | 塌方形态（若缺） |
|----|--------|------------------|
| 启动链 | 1+2 | 起错进程或就绪假死 |
| 投递链 | 4（依赖 1 的身份查询） | 覆盖在飞推理 / 消息滞留 |
| 判活链 | 3（依赖 1 的身份查询） | 活会话被误判死 |
| 自愈链 | 1+3 | 引擎翻转 |
| 上下文链 | 5 | 空脑运行 |
| 观测评估链 | 6 | 静默假阴性 |
| codex 并存 | 7（回退兼容） | 孤岛回归被破坏 |

层间依赖是**单向**的：第 1 层是 2–5 层的输入（没有 engine 事实源，「按引擎分派」无从谈起）；第 7 层保证第 1 层写入的事实不被推断覆盖。这就是「按最根本排序」的工程含义：从 1 开动，任何层的验收都要在 1 落地后才有意义；反序施工会做出一堆「按引擎」的假分派。

## 五、验证设计（命题 → 证据协议）

通用证据规则：真机 tmux 探针；一次性角色名（oc-test-*）；用后即清；证据保留 pane 捕获帧与命令输出；探针脚本以文件为载体、变量不经外层 shell 转义（工具链实证教训：外层会展开探针变量并污染工作区）。

| 命题 | 证据协议 |
|------|----------|
| P1 | 双引擎各走一遍六链（启动→投递→判活→自愈→上下文→状态），逐链留证 |
| P2 | ① persona 默认生效（不带覆盖参数起 opencode 角色）② CLI 覆盖生效（claude 角色 + 引擎参数起 opencode）③ 哨兵 engine 字段与选择一致 |
| P3 | 故障注入：kill opencode 进程触发自愈 → 重启后进程名仍为 opencode、哨兵 engine 不变 |
| P4 | claude 全链对照（启动/投递/判活/上下文/评估行为与改动前等价）+ claude 分支改动面审查（逐字不动的证明） |
| P5 | 对 opencode 会话触发评估入口 → 显式「未纳入评估」标记出现在状态可见面 |
| P6 | codex 子命令冒烟（start/exec/status）行为不变 |

## 七、术语表

- **引擎（engine）**：承载角色会话的 CLI 程序（claude / opencode / codex）。本方案的选择对象；与 opencode 内部的 `--agent`（其内置子代理）是两个层级。
- **同级**：生命周期操作集合与语义对两引擎一致（创建/投递/判活/自愈/上下文/状态），非「都能跑」。
- **声明 / 选择 / 事实源**：角色默认（persona 字段）、按次覆盖（CLI 参数）、持久真相（哨兵 engine 字段）。消费规则：只读事实源。
- **哨兵（sentinel）**：每会话一份的运行时记录（角色、tmux 名、pid、engine 等），跨进程的会话事实载体。
- **引擎翻转**：自愈路径把 A 引擎会话救成 B 引擎的故障；表现为身份/上下文/模型配置三重错位且监控显示「已恢复」。
- **判活 / 双检**：确认 agent 真实存活的检查；双检=tmux 会话存在 + pane 内引擎进程存活（wrapper 常驻导致「pane 活 ≠ agent 活」）。
- **忙判据**：从 pane 输出识别「正在生成勿投」的标志串（claude: "esc to interrupt"/"Retrying attempt"；opencode: "esc interrupt"）。
- **composer**：TUI 底部输入区；投递后须确认文本已离开该区才算提交（两引擎几何不同）。
- **工作区指令文件**：agent 启动时自动读入的工作目录级指令（claude: CLAUDE.md；opencode: AGENTS.md）。
- **wrapper**：包住引擎的 shell 重拉循环（进程退出后按退避重拉），判活双检的动因。
- **9Router**：本地模型路由网关，两引擎共用的模型出口。
- **TUI-in-tmux / 无头模式**：前者=tmux 承载交互式 TUI（持久会话）；后者=一次性执行命令（opencode run，无会话延续）。
- **显式降级**：能力不足处显式标注「未覆盖」并进可见面，替代静默跳过。
- **假阴性 / 假闲**：评估缺席被误读为合格；生成中被误判为空闲。两者都是「静默错误」，本方案明令禁止。
- **反推推断**：从会话名前缀猜引擎；合法用途仅限「无哨兵事实源时的兜底」。
- **孤岛**：与主链路平行、不共享生命周期操作的实现形态（codex 现状）。
