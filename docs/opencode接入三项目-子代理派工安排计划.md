# opencode 接入三项目 — 子代理派工安排计划（并发编排 · 三方六维度监控）

> 本篇是第四份文书。四篇分工：**审计稿**=现状因果链与修改论证；**计划书**=成功判据（P1–P6）与七层根因论证；**任务书**=工作包与验收契约；**本篇**=派工拓扑设计——谁改哪些文件、并行到什么程度、审查如何在并发下不失效、失败如何回滚。配套《子代理提示词集》为可修改的派发原文。
> 本篇遵循同一质量合同：逻辑链完整、真实数据证据、代码逻辑佐证、按最根本排序、不贴代码只讲逻辑。

## 〇、为什么「派工安排」必须独立成篇（而不是任务书的一节）

派工本身是一个设计变量，不是行政动作。错误的并发会产生三类新缺陷：**文件争用**（两个代理改同一文件，后写覆盖先写或语义撕裂）、**契约漂移**（各轨对同一接口各自猜测，集成时才发现字段名/语义不一致）、**审查串供**（审查代理采信实现代理的口头解释，把"说得圆"当"做得对"）。正确的并发把反馈环从"全批一个环"切成"每轨一个环"——定位粒度变细、返工面变小。

因此：安排必须**先论证拓扑与边界，再执行派发**；这不是任务清单，而是并发安全性论证。执行动作（派发）在本篇与提示词集落盘后立即进行。

## 一、拆轨原则：按爆炸半径与文件所有权拆，不按「最好修」拆

**术语**：
- **爆炸半径**：一处改动在语义上波及的运行路径集合。爆炸半径大的改动（如 core.start）不适合与它的消费者并发改。
- **文件所有权**：每个实现轨独占一个文件集合，任何轨不得修改白名单外文件；跨轨需求一律走**契约接口**并经主代理流转。这是并发安全的第一道闸。

**四轨划界与论证**：

| 轨 | 使命 | 文件所有权 | 为何这样划 |
|---|---|---|---|
| A 身份与启动面 | 第1+2层：引擎成为一等概念 + 按引擎分派启动 | persona JSON（hermes-session-roles）、ccs.py、core.py、ops/sentinel.py（session-launcher） | 引擎身份的声明点（persona）、选择点（ccs.py）、消费点（core 启动分派）、事实源（哨兵）全部集中在此集合。不把 routing/roles.py 划给 A：那是落盘语义，与 C 耦合，划开会争文件。 |
| B 判活/自愈/TUI判据 | 第3+4+7层：按引擎取进程名与 TUI 判据、防引擎翻转 | tmux_ops.py、ops/watchdog.py、ops/ecosystem_health.py | 21 处 claude 字面量的判活/自愈面集中在此。不碰 core.py 的启动配方（A 的地盘），对启动入口只做契约调用。 |
| C 上下文落盘 | 第5层：按引擎写 CLAUDE.md/AGENTS.md，内容同源 | routing/roles.py（session-launcher） | 唯一的上下文写入入口在此（inject_role_knowledge_into_workspace）。partner.py 经核查无上下文写点，不划入（防无谓爆炸半径）。 |
| D 评估面显式降级 | 第6层：opencode 会话评估不静默假阴性 | session-pipeline：pipeflow/role_lifecycle.py、eval_checker.py、wf_lifecycle.py 及 eval 最小配套 | 与 A/B/C 天然不同项目目录，文件集合零交集，是四轨中唯一可以完全独立并行的轨。 |

**反面论证（为何不按"七层"开七轨）**：层是**因果序**（根本先于表层），不是工作面。第 3、4、7 层共用 tmux_ops.py，按层拆轨必然多轨争用同一文件。层序的语义改由两件事承担：①轨内顺序（见第二节）；②契约冻结（见第四节）先把第 1 层的接口定死，使表层轨可以安全先行编码。

**反面论证（为何不合成一个大轨串行）**：串行只有一个反馈环，审查只能在末态一次进行，定位粒度=全批；且总耗时=各轨之和。并发后每轨一个反馈环，审查随完成触发，总耗时≈最长轨。

## 二、依赖结构：真依赖与假依赖

**真依赖**（无法通过排工消除）：引擎契约未冻结之前，任何轨写代码都是在猜接口——猜错=契约漂移=集成期集体返工。**处置：把真依赖前置为一次契约冻结**（第四节，随本篇同时定稿）。此后四轨对同一份契约编码，真依赖被转化为"集成期校验"，并发达成。

**假依赖**（排工可消除，因此必须并行）：
- B ↔ C：无数据流、无文件交集。判活与落盘互不调用。
- C ↔ D：无数据流。落盘在 launcher，评估在 pipeline。
- A ↔ B：文件不相交。B 的自愈路径会调用启动入口并传 engine（契约参数名已冻结），这是契约调用，不是对 A 代码的依赖——A 未落地时 B 可先完成不依赖该参数的部分并如实标注（见提示词 B 异常协议）。

**轨内层序**（根本→表层，轨内串行）：
- A 内：第 1 层（身份声明）→ 第 2 层（启动分派）。没有身份就没有分派可言。
- B 内：第 4 层（判据表）→ 第 3 层（判活/自愈用判据）→ 第 7 层（命名/进程名解耦收尾）。自愈依赖判据先存在。
- C 内：同源生成器 → 按引擎路由落盘。
- D 内：引擎判定通道 → 降级语义 → 现状路径回归确认。

**旧结论不当锚点（每轨强制 Phase 0 重验）**：每轨编码前先在自己的范围重验锚点清单（见提示词各轨 Phase 0 节），任何一条与现实不符→停手、上报、待指示，禁止沿用历史结论继续写。筹备期已示范一次：`test_ecosystem_health_engine.py` 文件名疑似引擎先例，重读内容后确认其测的是**工作流引擎判活**——旧印象被推翻。

## 三、术语碰撞警示（专业名词，B 轨特别注意）

本代码库中「引擎（engine）」有两个互不相关的含义：

1. **会话承载引擎**：claude / opencode / codex —— 决定用哪个 CLI/TUI 进程承载一个会话。这是本次改造的对象；哨兵 `engine` 字段的语义即此。
2. **工作流引擎（wf:engine）**：workflow daemon 的判活概念（`_check_workflow_engine`，"MainPID 是否真持有 workflow-daemon.lock"）。`tests/test_ecosystem_health_engine.py` 测的是它，与会话承载引擎**无关**。

**约束**：轨 B 修改 ecosystem_health.py 时严禁把两种语义混同（例如把 wf:engine 判活改成按会话引擎查表）；wf:engine 的三条既有测试必须持续通过。任何文书/代码注释提到 "engine" 时必须能从上下文分辨指哪一个。

## 四、冻结契约（四轨共同遵守；含「为何能解决」的因果）

### 4.1 engine 取值域与语义
取值域 `{"ccs", "opencode", "codex"}`。**ccs**=claude 承载引擎的历史名（沿用，零改动）；**codex** 既有值不动；**opencode** 新增。语义=该会话由哪个承载引擎运行。哨兵 `engine` 字段已存在（默认 "ccs"，写入/读取通道已在，落 `~/.hermes/run/ccs-sentinels/{role}.json`）——**缺的不是字段而是闭环消费**，这正是第 1 层根因（身份无处声明、声明了无人读）。

### 4.2 三层声明数据流（D2）
`persona.engine`（角色默认，可选字段，缺省语义 "ccs"；存量 persona 显式补 `"engine":"ccs"`）→ `ccs.py start --engine`（按次覆盖，优先级最高）→ **哨兵 engine = 事实源**（启动编排收尾时落盘）。
**自动重启只读哨兵，永不回读 persona。** 为何能解决引擎翻转：翻转的根因是重启路径重新走"默认拉 claude"的启动函数；钉死事实源后，重启继承会话原身份，persona 后续怎么改都不影响在途会话。

### 4.3 引擎注册表（查表代替字面量）
每个引擎一行注册数据，字段：进程名/comm、忙标记文案、composer 几何、提交确认方式、上下文文件名、启动配方。实测数据（18:18–18:25 重验复现）：

| 字段 | ccs（claude） | opencode | codex |
|---|---|---|---|
| 进程名/comm | claude | opencode | （不动） |
| 忙标记 | "esc to interrupt" / "Retrying attempt" | "esc interrupt"（实测，无 to） | （不动） |
| composer 几何 | 双横线 | 竖线（实测） | （不动） |
| 提交确认 | Enter + composer 清空确认 | Enter 提交（实测成功） | （不动） |
| 上下文文件 | CLAUDE.md | AGENTS.md（实测只认此文件） | （不动） |
| 启动配方 | 现行 wrapper 原样（claude --model 9router_hermes + 9router env 注入） | 工作区 cwd 直接拉 `~/.opencode/bin/opencode`（TUI-in-tmux，D3）；9router 已在 opencode.jsonc 配好，**不需要** env 注入 | （孤岛不动） |

**为何能解决**：21 处 claude 字面量是同一个根因（身份无处查询）的 21 个症状。全部改为查注册表后，新增引擎=加一行表，而不是再挖一座 codex 式孤岛；opencode 与 claude 的启动不对称（env 注入与否）是**表数据差异**而非逻辑分叉，主流程只有一条。

### 4.4 命名空间（D1）
tmux 会话名继续 `ccs-` 前缀；pipeline liveness 的 ccs- 过滤**零改动**。engine 不编码进会话名：会话名是资源定位符，引擎是实例属性；混写会让"换引擎"变成"改名断链"（send/liveness/feed 的活跃集合全部按名索引）。

### 4.5 跨轨接口（并发安全核心，字段名冻结）
- **A 提供**：`StartOptions.engine`（默认 "ccs"）；`ccs.py start --engine {ccs|opencode|codex}`；**机器取数面 = `ccs.py status-role <role>` JSON 与 core.status() dict，每会话补 engine 字段**；`ccs.py status` 文本视图仅追加 engine 展示（只增不改）。【18:5x 修正：此前括注"status 现状本就输出 JSON"经 T1A Phase 0 重验**不成立**——status 子命令是文本人读视图（ccs.py:314-334），status-role 才是 JSON 机器视图（ccs.py:416-420，pipeline routes.py:473 已按 JSON 消费），core.status() 返回 list[dict]。engine 一律从哨兵事实源读，读不到时按前缀反推兜底并标注来源（如 engine_source 字段），不静默编造。】启动成功后最终 engine 写入哨兵。
- **B 提供**：按 engine 解析进程名/comm 与 TUI 判据的单一查询入口（本轨模块内）；自愈路径经 `engine` 参数调用启动入口（参数名以 A 的签名为准）。
- **C 提供**：按 engine 选上下文文件名的映射 + 同源内容单份生成写入。
- **D 消费**：**经 `ccs.py status-role <role>` JSON 的 engine 字段**判定会话引擎（不解析 status 文本）；ccs→读转录（现状零改动）；opencode（及 codex/未知）→显式降级。

### 4.6 零回归判据（影响面维度）
claude 路径六链（启动/投递/判活/重启/上下文/评估）行为改动前后同型；codex 岛零文件改动；liveness ccs- 过滤零改动；wf:engine 三条测试持续通过；**三仓存量测试全量跑通**（python3 -m pytest，9.1.1，PATH 无全局 pytest 但模块可用）。

### 4.7 回滚协议（git 事实，18:44 核查）
三项目皆 git 仓：session-launcher（分支 r77-routing-daemon-whitelist）、session-pipeline（temp-pr-branch）、hermes-session-roles（main）。开工时各仓建 `feat/opencode-engine` 工作分支；**存量脏文件不动**（launcher: 1 个未跟踪 .bak 文件；pipeline: .test_reports/last_result.json；roles: README.md——均为本次之前已存在的状态）。每轨按逻辑单元 commit（信息带轨号 T1A/T1B/T1C/T2D），只 `git add` 自己的文件、禁止 `git add -A`——回滚=按轨 revert。**证据先行**：无证据目录产物=未完成。

## 五、派工拓扑与并发时序

```
阶段0  契约冻结（本篇第四节）────────────── 已完成
阶段1  四轨并行编码：  A ─┐ ├─ B ─┤ ├─ C ─┤ └─ D（实现并发）
阶段2  轨级盲审随完成触发： A完成→盲审A ┐（与他轨编码并行）
                                B完成→盲审B ├ 互不等待
                                C完成→盲审C ┘
阶段3  批次一闸门：盲审A+B+C 全过 → 主代理终审（六维度合成）→ 才放行
        集成冒烟（跨轨行为：重启不翻转 / status含engine / 双引擎拉起）
阶段4  D 的盲审 → 终审 → 交付包（D 的实现虽已并行完成，裁决押后）
```

**为何 T2（轨 D）实现并发、裁决串行**：D 的文件与三轨互斥、所需语义已被契约冻结→编码期无冲突，这是真并行收益。但「显式降级判得对不对」依赖引擎身份判定是否正确（身份层在 T1）——若 T1 未过审就裁决 D，身份层缺陷会被误判为降级缺陷（或反之），产生级联误判。**并发省的是编码时间，串行守的是判定因果。**

**为何盲审可与他轨编码并行**：盲审对象是已完成轨的 diff+证据，与他轨文件无交集；盲审代理与实现代理上下文隔离（防串供=防"实现代理解释带偏审查"）。

**为何批次一闸门不可省**：四轨拼合后的跨轨行为（重启不翻转、status 含 engine）单轨都验不了；必须在三轨过审后做一次集成冒烟，这是 D5"五链同级"的最终实证。

## 六、三方六维度在并发下的执行编排

**三方**：①实现轨子代理（写码+自检+证据）②交叉盲审子代理（独立上下文，只看 diff+文书+证据，禁止采信实现代理解释）③主代理（监控+裁决，不写一行代码）。

**六维**（沿任务书判据）：正确性 / 完整性 / 一致性 / 影响面与零回归 / 实证性 / 防退化。

**监控点位（主代理，触发任一即停批）**：
1. Phase 0 锚点失效上报；2. 跨轨契约歧义上报；3. 盲审不通过；4. 任何 claude 回归迹象；5. 生产会话（ccs-consumer/engineer/scout，18:44 实录存活）被波及迹象；6. 同一问题三修失败。

**审查粒度论证**：不采用"全部写完一起审"——审查上下文会爆炸、定位粒度变粗、返工面扩大。轨级盲审把定位钉在轨内，批次终审只做跨轨合成与命题（P1–P6）核验。

## 七、失败、停机、探针卫生（运维事实纪律）

- **三次失败暂停**：同一问题修 3 次不过→停手→上报→裁决。
- **测试会话**：一律一次性角色（如 ccs-t1a-smoke），用完即 kill；禁用生产角色名拉测试实例；禁触 cdx-* 会话。
- **WSL 操作须知（真实教训）**：命令一律先 Write 脚本到 `\\wsl.localhost\Ubuntu\tmp\*.sh`，再用 PowerShell 工具执行 `wsl -d Ubuntu -- bash /tmp/xx.sh`；**严禁把 $ 变量内联进 `wsl ... bash -lc '...'`**（外层展开，上轮探针 marker 落错目录的根因）；Git Bash 会转换 /tmp 路径，故不用 Bash 工具触发 wsl 脚本；opencode 二进制用 `~/.opencode/bin/opencode` 绝对路径。
- **证据目录**：`C:\Users\Administrator\WorkBuddy\2026-11-13-16-01-58\evidence\<轨名>\`（WSL 侧同路径 /mnt/c/...）。探针 marker 只进 /tmp 与 evidence，用后即清。
- **git 并发注意**：三轨同仓提交可能遇 index.lock 竞争——遇锁稍候重试，不强删锁文件。
